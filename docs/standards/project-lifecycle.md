# Project Standard & Lifecycle

Это канонический стандарт Bruce-проектов, созданных из `dedtsss/etalon-project-template`.

Цель: каждый новый проект начинает работу по одной лестнице, хранит решения и идеи в GitHub и не зависит от памяти конкретного чата или агента.

## 1. Источник истины

GitHub-репозиторий проекта является источником истины: код, конфигурация, Issues, Pull Requests, Actions и проектные документы.

Внешняя память, чаты и заметки могут помогать восстановить контекст, но не заменяют GitHub. Если внешний контекст расходится с репозиторием, сначала проверить актуальное состояние GitHub и затем исправить устаревший документ.

Роли основных документов:

- `AGENTS.md` — короткие обязательные правила работы агента;
- `docs/status.md` — текущее состояние проекта и ближайший следующий шаг;
- `docs/decisions.md` — уже принятые продуктовые/архитектурные/процессные решения;
- `docs/ideas.md` — идеи, prior art и результаты исследований, которые ещё не обязательны;
- GitHub Issues — конкретные задачи и acceptance criteria;
- `docs/specs/` — спецификации крупных или неоднозначных изменений;
- `docs/backlog.md` — обзорная очередь, если она нужна проекту;
- `docs/standards/` — общие правила, выбираемые по типу задачи.

## 2. Обязательный каркас проекта

Новый проект создаётся через GitHub `Use this template` из `dedtsss/etalon-project-template`, а не из пустого репозитория вручную.

Минимально обязательны:

```text
.etalon-version
README.md
AGENTS.md
CODEX.md
.github/
docs/
  status.md
  backlog.md
  decisions.md
  ideas.md
  standards/
    index.yml
    project-lifecycle.md
  specs/
scripts/
  check.sh / check.ps1
  doctor.sh / doctor.ps1
```

Проект может добавлять любые свои файлы. Обязательный каркас не должен удаляться без осознанного решения.

## 3. Лестница нового проекта

### Шаг 0 — Идея

Коротко определить:
- для кого продукт;
- какую проблему решает;
- что является результатом для пользователя.

### Шаг 1 — Prior art до разработки

Проверить, не решена ли задача раньше:
- готовые продукты и open source;
- официальная документация;
- Issues / PR / Discussions / changelog / forks;
- ограничения платформы, лицензий, API и эксплуатации.

Полезные находки записать в `docs/ideas.md`.

### Шаг 2 — MVP и границы

Зафиксировать:
- MVP;
- что сознательно не входит в MVP;
- основной стек и причины выбора;
- критические риски: данные, безопасность, стоимость, внешние API, переносимость, ограничения платформ.

Существенные принятые решения записать в `docs/decisions.md`.

### Шаг 3 — Создание репозитория

Создать репозиторий через `Use this template`.

Сразу заполнить:
- `README.md`;
- `docs/status.md`;
- проектный профиль в `AGENTS.md`;
- команды build/test/check;
- реальные ограничения и deployment boundary.

Не начинать крупную реализацию, пока базовый контур проекта не описан.

### Шаг 4 — Постановка работы

Для отдельной функции/исправления создать GitHub Issue с целью и проверяемыми acceptance criteria.

Для крупной/неоднозначной задачи сначала создать spec в `docs/specs/` или эквивалентный подробный task-файл.

### Шаг 5 — Реализация

Работать в focused branch/PR.

До изменения архитектуры или крупной функции агент обязан просмотреть:
1. релевантные решения в `docs/decisions.md`;
2. релевантные идеи в `docs/ideas.md`;
3. соответствующие стандарты и профильную документацию.

Не перепридумывать уже принятое решение без новой причины/доказательства.

### Шаг 6 — Проверка

Запустить минимально достаточные релевантные тесты, затем `scripts/check` или эквивалентный единый project check.

Для пользовательского интерфейса проверять не только функциональность, но и реальное отображение на целевых viewport/device, когда это применимо.

### Шаг 7 — Review и завершение

PR должен содержать:
- что изменено;
- что проверено;
- что не проверено;
- риски/ограничения;
- ссылку на Issue/spec.

Merge/deploy выполняются только в соответствии с полномочиями конкретной задачи.

### Шаг 8 — Durable handoff

После существенного этапа обновить только то, что действительно изменилось:
- `docs/status.md` — текущий статус и следующий шаг;
- `docs/decisions.md` — новое принятое решение или `superseded` старого;
- `docs/ideas.md` — найденная идея/результат исследования/статус реализации;
- Issue/PR — итог и evidence.

Чат не должен оставаться единственным местом, где существует важное решение.

## 4. Ideas vs Decisions vs Backlog

`ideas.md` отвечает на вопрос: «Что мы нашли или можем сделать?»

`decisions.md`: «Что уже решили и почему?»

GitHub Issue/backlog: «Что реально собираемся делать и как поймём, что готово?»

Одна идея не становится задачей автоматически. Принятая идея должна получить решение и, если требуется реализация, Issue/spec.

## 5. Изменение уже принятого решения

Старое решение не удалять молча.

Пометить его как `superseded`, добавить новое решение, причину изменения и evidence. Это защищает проект от циклического возвращения к уже отвергнутым вариантам.

## 6. Старые проекты

Старый проект не требуется перестраивать целиком за один PR. Приведение к стандарту выполняется постепенно и без ломки продукта.

Минимум для признания проекта стандартизированным:
- `AGENTS.md`;
- `.etalon-version`;
- `docs/status.md`;
- `docs/decisions.md`;
- `docs/ideas.md`;
- GitHub Issue/PR workflow;
- единая команда проверки или явно документированный эквивалент.

## 7. Контроль дрейфа

`.etalon-version` показывает, к какой версии каркаса приведён проект.

`scripts/doctor.*` должен падать, если отсутствуют обязательные файлы шаблона. Это не доказывает качество проекта, но не позволяет незаметно потерять базовую структуру.

Периодически можно проводить аудит существующих репозиториев по этому стандарту и обновлять их отдельными безопасными задачами.
